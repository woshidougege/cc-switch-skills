# Codex 开发提效

## 定位

这是一个执行策略 Skill：决定如何压缩上下文、何时委派子 Agent、如何使用 Goal、选择哪些 Codex 原生能力，以及如何集成和验收。

它不替代：

- `AGENTS.md` 和用户明确指令。
- `dev-requirements` 等项目通用规则。
- 分支、MR、构建、测试和发布领域的专用 Skill。
- 具体业务、语言、框架或外部系统 Skill。

冲突优先级：

```text
用户明确指令
  > 项目 AGENTS.md / 专用 Skill
  > 本 Skill 的通用提效策略
```

本 Skill 不得降低质量门槛、扩大写入权限或绕过审批。

## 核心原则

1. 目标是缩短 wall-clock time，不是节省 Token、增加 Agent 数量或输出长度。
2. 主 Agent 负责目标、最小侦察、上下文压缩、关键路径、集成和最终验收。
3. Context first：先让主 Agent 形成可复用的上下文包，再委派子 Agent。
4. 子 Agent 应继承足够的上下文，并接收边界明确、可独立验证的窄任务。
5. 更多 Token 用于高质量上下文通常比让 Agent 重新扫描仓库更快；不要为了省 Token 增加往返。
6. 同一任务不重复研究、不重复实现、不让多个 Agent 争用同一写入范围。
7. 子 Agent 结论都必须有证据；主 Agent 必须读取 diff、日志或测试结果后复核。
8. 优先使用已有 Skill、MCP、插件、连接器和原生工件能力，再考虑手工流程。
9. 简单任务、强顺序任务或单一慢外部操作，单 Agent 通常更快。

## 任务分级

### 单 Agent

适用：

- 单文件或少量文件的小改动。
- 下一步完全依赖上一步结果。
- 只有一个慢操作，例如等待构建、部署或外部接口。
- 多个 Agent 会修改同一共享文件或状态。
- 需求仍在快速变化，拆分后很快失效。

### 2 至 4 个子 Agent

适用：

- 大仓库中多个模块或调用链互不重叠。
- 一个复杂问题有多个可并行验证的假设。
- 功能可以按独立模块或互斥文件拆分。
- 构建、测试、浏览器验证、评审可以并行。
- 需要同时查仓库、官方文档、CI 日志或历史记录。

默认只为真实独立工作流启动子 Agent。不要为了并行而拆成“一文件一个 Agent”。

### 长任务或隔离任务

- 需要与本地未提交改动隔离时，可使用 worktree；涉及用户可见的主工作区/worktree 切换时先征求确认。
- 子 Agent 的内部 fork 由 Codex 管理，不额外视为切换用户主工作区。
- 需要电脑休眠后继续运行、且环境已具备时，可建议 Codex Cloud。
- 周期性检查或长任务完成后继续，可使用 automation；一次性任务不要创建自动化。

## Goal 与 Token 策略

### 普通任务默认不建 Goal

Goal 用于跨多轮持续探索、下一步依赖前一步发现、需要持久目标的复杂任务。普通修复、代码审查、一次性调查和小功能直接执行，不创建 Goal。

Plan 负责路径，Goal 负责持续到某个结果；不要用 Goal 替代任务计划。

### 禁止自行设置 Token 上限

- 不得自行传入 `token_budget` 或其他 Token 预算。
- 只有用户明确给出具体预算数值时才设置。
- 用户当前使用自部署推理资源，Token 无限；默认以执行时间和结果质量优先。
- 不得因为“担心 Token”缩减必要的上下文、测试、Review 或并行覆盖。
- 已存在的 Goal 被预算阻塞不代表任务完成；应明确报告，并用无预算 Goal 或普通任务继续。

### Goal 可创建的条件

仅在以下情况考虑 Goal：

- 用户明确要求创建 Goal。
- 任务需要跨多轮持续尝试，且成功条件可由测试、日志、基准或工件证明。
- 路径不确定，但目标、边界和停止条件都清楚。

创建 Goal 时必须包含：

- 可验证的结果。
- 验收表面，例如测试、构建、日志、页面或最终工件。
- 文件、工具和数据边界。
- 可能阻塞时需要的用户输入。
- 证据不足时不得标记完成。

## 委派前门槛

主 Agent 先做最小侦察，再决定是否启动子 Agent。委派前至少要准备：

1. 用户目标与成功标准。
2. 已经确认的事实和证据。
3. 相关仓库、模块、文件或命令入口。
4. 已知假设、失败方向和已经排除的路径。
5. 子任务边界、禁止范围、写入范围和停止条件。
6. 验证方式和期望输出。
7. 哪个 Agent 是只读，哪个允许修改。

缺少第 1、3、5、6 项时，不要把整个仓库探索丢给子 Agent；主 Agent 先完成一次最小侦察。

## 子 Agent 上下文继承

### 默认继承主线程

- 当前子 Agent 工具如果支持 fork/inherit context，复杂任务默认开启。
- 即使继承了主线程，仍要提供精简 Context Packet，明确指出本次任务最重要的已知事实。
- 不要让子 Agent 从聊天历史中自行猜哪段最重要。

### 独立评审例外

验证或评审 Agent 可以不继承完整实现历史，以防只证明实现正确。此时必须在提示中提供：

- 原始用户需求。
- 最终 diff。
- 验收标准和测试命令。
- 已知风险与改动范围。
- 要求其独立寻找反例。

## Context Packet

每次委派应包含以下内容：

```text
【上下文】
你继承了主线程上下文，但不要重新扫描无关仓库。

【用户目标】
<最终要解决的问题>

【已确认事实】
- <事实 + path:line / 命令输出 / 文档链接>
- <已排除的方向>

【相关文件】
- <绝对或仓库相对路径>
- <最多列最关键的若干项>

【本次任务】
<一个明确、窄、可验证的交付物>

【范围】
- 只读：<允许读取的文件/目录/系统>
- 写入：<允许修改的文件；无写入写“禁止修改”>
- 禁止：<不得检查或修改的范围>

【约束】
- 项目规则、PowerShell、分支、安全要求
- 不得重复已经完成的调查

【验收】
- 必须运行的命令、测试或页面流程
- 必须返回的原始证据

【停止条件】
- 达到文件/命令/假设范围仍无法判断时，停止并报告缺少什么
- 不自行扩展成全仓审计

【输出】
结论、证据、改动文件、验证结果、风险、未完成项
```

## 委派规则

1. 每个 Agent 只负责一个主要交付物。
2. 任务必须窄而有边界，禁止“全面分析”“优化一下”“看看有没有问题”这类开放式委派。
3. 用文件数、模块数、命令数或假设数限制范围；超过范围时先返回中间结论。
4. 已经确认的路径和结论直接放进 Context Packet，不要求 Agent 重新发现。
5. 只读任务可并行；写任务必须有互斥写入范围。
6. 编码型子 Agent 在独立 fork 或隔离工作区修改，并列出全部改动路径。
7. 如果 Agent 开始扩大范围，主 Agent 用 `send_input` 补充上下文并立即收窄，不要新开一个重复 Agent。
8. 子 Agent 输出只作为输入，不能替代主 Agent 的最终验证。

## 推理强度与模型

当前环境允许配置模型或 reasoning effort 时，按耗时和难度分配：

| 任务 | 建议 |
|---|---|
| 文件定位、日志筛选、简单扫描 | 低或中 reasoning |
| 普通实现、测试分析 | 中 reasoning |
| 根因、架构、并发、安全、最终 Review | 高 reasoning |
| 极难且证据充分的专项问题 | 高以上，确有收益再使用 |

不要所有 Agent 都使用最高推理；这会增加等待时间。未明确配置时，子 Agent 通常继承父 Agent 的设置。

## 委派模板

### 侦察模板

```text
只读完成 <一个具体问题>，不要修改文件。
你已继承主线程上下文，不要重新扫描整个仓库。
先检查：<最多 3~6 个文件、目录或命令入口>。
需要验证的假设：<1~3 个>。
若这些信息不足，停止并说明缺少的证据，不要自行扩大范围。
返回：path:line、关键输出、结论、仍不确定点。
```

### 实现模板

```text
实现 <一个窄子任务>。
只允许修改：<文件或目录>。
已确认接口/结论：<上下文包>。
禁止修改：<共享文件和其他模块>。
完成后运行：<构建/测试>。
返回：实际改动路径、关键 diff、验证结果、剩余风险。
```

### 验证模板

```text
独立验证 <改动>，不要假设实现正确。
输入：<最终 diff、需求、验收标准、测试命令>。
重点：<回归、边界、并发、权限、视觉宽度等>。
只检查本次改动及其直接影响，不重扫整个项目。
返回：通过/失败、原始证据、失败步骤、最小修复建议。
```

## 执行流程

1. 读取项目规则，确认仓库、分支、工作区、未提交改动和可用工具。
2. 写明成功标准与验证面。
3. 主 Agent 先做一次最小侦察，形成 Context Packet。
4. 判断单 Agent 还是并行；只按真实独立工作流启动 2～4 个 Agent。
5. 子 Agent 默认继承主线程上下文，并把窄任务和停止条件放进提示。
6. 子 Agent 运行期间，主 Agent 继续处理关键路径、集成或测试准备，不空闲等待。
7. 只有被结果阻塞时使用当前环境的 Agent 等待/汇总工具，不反复轮询。
8. Agent 超范围时用 `send_input` 收窄，不重复创建任务。
9. 审查结果；拒绝无证据、超范围或验证失败的结果。
10. 运行最终质量门禁和独立 Review。
11. 关闭不再需要的 Agent，清理临时资源，输出精简交付说明。

## 工具选择

| 需求 | 优先方式 |
|---|---|
| 固化项目规则 | `AGENTS.md`、仓库级 Skill |
| 复用流程 | 已有 Skill；没有再用临时提示 |
| 并行调查 | 上下文充分的子 Agent |
| 互斥模块实现 | 子 Agent + 独立写入范围 |
| 后台隔离开发 | worktree；用户可见切换先征得确认 |
| 主工作区构建/运行/调试 | IDEA MCP |
| worktree 构建/测试 | PowerShell `mvn` |
| 代码评审 | `/review` 或独立评审 Agent |
| 前端真实验证 | 浏览器、CDP、真实 Chrome、截图和 Console/Network |
| 周期检查 | automation；先手工验证，再保存 |
| 外部系统 | MCP、插件或连接器 |
| 长时隔离任务 | Codex Cloud，前提是用户和要求允许 |
| 文档/表格/PDF/演示 | 对应文档工件 Skill |
| 官方能力核对 | `openai-docs` Skill |

不要同时启动多个会写同一工作区、数据库记录或外部系统的子任务。

## 自动化提效

只有任务会重复发生且用户明确要求自动化时，才建议 automation：

- PR/CI 持续巡查。
- 新评审意见跟进。
- 部署或长任务完成提醒。
- 周期性日志、依赖或安全扫描。
- 日报、周报和固定格式报告。

不得自行创建或修改 automation；用户确认后，创建前：

1. 先用普通任务手工验证提示和访问权限。
2. 明确什么变化值得通知。
3. 状态未变化或不可操作时保持静默。
4. 需要用户决定时再提醒，不制造周期性噪声。
5. 更新已有自动化前先确认是否重复。

## 质量门禁

至少执行与改动风险匹配的验证：

- 读取最终 diff，而不只看子 Agent 摘要。
- 运行项目指定的构建、类型检查和测试。
- 前端不能只依赖类型检查；按项目要求做真实浏览器验证。
- 检查失败日志原文，不把“HTTP 200”或“命令返回”当成业务成功。
- 检查敏感信息、调试代码、本地配置和开发者模式内容。
- 检查分支、MR 目标和提交范围是否符合专用 Skill。
- 合并或交付前由主 Agent 做最终独立复核。

## 禁止事项

- 不因为提效跳过需求确认、构建、测试或 Review。
- 不自动 commit、push、merge、deploy 或修改生产数据。
- 不给子 Agent 只有任务标题、没有上下文和边界的委派。
- 不让子 Agent 重新扫描已经由主 Agent 调查过的无关区域。
- 不在多个 Agent 间共享未锁定的写入范围。
- 不为达到 Agent 数量而拆分任务。
- 不让子 Agent 在后台运行后无人检查结果。
- 不创建用户可见 thread 来替代内部子 Agent；除非用户明确要求新 thread。
- 不自行创建 Goal 或设置 Token 上限。
- 不重复创建已有 automation。
- 不把子 Agent 总结当成证据。
- 不隐藏失败、跳过项和残余风险。

## 完成回报

最终回复保持精简，至少包含：

```text
完成：做了什么
验证：构建/测试/浏览器/评审结果
改动：关键文件或 MR
风险：未验证项、失败项、需要用户决定的事项
```

如果所有检查通过，明确写“通过”；如果有未验证项，写清原因和影响，不得用“应该没问题”代替证据。
