# Codex 开发提效

## 定位

这是一个执行策略 Skill：决定如何拆分任务、何时使用子 Agent、选择哪些 Codex 原生能力，以及如何集成和验收。

它不替代：

- `AGENTS.md` 和用户明确指令。
- `dev-requirements` 等项目通用规则。
- 分支、MR、构建、测试和发布领域的专用 Skill。
- 具体业务、语言、框架或外部系统 Skill。

发生冲突时，优先级为：

```text
用户明确指令
  > 项目 AGENTS.md / 专用 Skill
  > 本 Skill 的通用提效策略
```

本 Skill 不得降低质量门槛、扩大写入权限或绕过审批。

## 核心原则

1. 目标是缩短实际耗时并提高覆盖度，不是增加 Agent 数量或输出长度。
2. 主 Agent 负责目标、拆分、关键路径、集成、冲突处理和最终验收。
3. 子 Agent 只处理边界清晰、可独立验证的子任务。
4. 非简单任务先寻找并行机会；存在至少两个真正独立工作流时，主动委派，不等待用户再次提醒。
5. 同一任务不重复研究、不重复实现、不让多个 Agent 争用同一写入范围。
6. 仅当当前会话提供子 Agent/多 Agent 工具时才委派；所有子 Agent 结论都要有证据，主 Agent 必须复核后才能采用。
7. 优先使用已有 Skill、MCP、插件、连接器和原生工件能力，再考虑手工流程。
8. 对简单任务、强顺序任务或单一慢外部操作，单 Agent 通常更快。

## 任务分级

### 单 Agent

适用：

- 单文件或少量文件的小改动。
- 下一步完全依赖上一步结果。
- 只有一个慢操作，例如等待构建、部署或外部接口。
- 多个 Agent 会修改同一共享文件或状态。
- 需求仍在快速变化，拆分后很快失效。

### 2 至 4 个子 Agent

适用：

- 大仓库中多个模块或调用链互不重叠。
- 一个复杂问题有多个可并行验证的假设。
- 功能可以按独立模块或互斥文件拆分。
- 构建、测试、浏览器验证、评审可以并行。
- 需要同时查仓库、官方文档、CI 日志或历史记录。

默认只为真实独立工作流启动子 Agent。不要为了达到数量而拆分。

### 长任务或隔离任务

- 需要与本地未提交改动隔离时，可使用 worktree；涉及用户可见的主工作区/worktree 切换时先征求确认。
- 子 Agent 的内部 fork 由 Codex 管理，不额外视为切换用户主工作区。
- 需要电脑休眠后继续运行、且环境已具备时，可建议 Codex Cloud。
- 周期性检查或长任务完成后继续，可使用 automation；一次性任务不要创建自动化。

## 并行模式

### 侦察

把只读调查拆给多个 Agent：

- 前端调用链。
- 后端接口和数据流。
- 测试、配置和构建入口。
- 日志、CI、历史提交或 PR。
- 官方文档和外部连接器。

要求每个 Agent 返回 `path:line`、命令输出或文档链接等证据。

### 实现

只按互斥写入范围拆分编码任务：

- 一个 Agent 一个模块、组件或目录。
- 明确禁止修改分配范围之外的文件。
- 先约定接口、数据结构、命名和验收条件。
- 主 Agent 处理共享接口、最终集成和跨模块冲突。
- 编码型子 Agent 在自己的 fork 或隔离工作区直接修改文件，并在结果中列出所有改动路径。

如果两个工作流必须修改同一核心文件，改为单 Agent 串行实现。

### 验证

可并行拆分：

- 构建和类型检查。
- 单元、集成和接口测试。
- 真实浏览器、页面宽度和交互验证。
- 回归、安全、性能、竞态和权限检查。
- CI 失败日志与历史基线对比。

验证 Agent 不得假设前一个 Agent 的说法正确；要独立运行命令或复现问题。

### 评审

复杂改动可启动独立评审：

- 正确性和业务逻辑。
- 回归与边界条件。
- 测试缺口。
- 安全、权限和敏感信息。
- 性能、并发和资源泄漏。

优先采用独立上下文评审，避免实现 Agent 只证明自己的实现正确。

### 外部研究

并行调查：

- 官方文档和版本兼容性。
- 当前仓库实现与依赖版本。
- GitLab/GitHub MR、CI、Issue。
- Jira、SharePoint、数据库元数据等连接器信息。

涉及 Codex 或 OpenAI 能力时，使用 `openai-docs` Skill，不靠记忆猜功能。

## 子 Agent 委派协议

每个委派至少包含：

```text
目标：要回答或完成的具体结果
范围：允许读取的文件、模块或系统
写入：允许修改的文件；只读任务明确写“禁止修改”
约束：项目规则、PowerShell、分支、安全要求
验证：必须运行的命令或证据
回报：结论、证据、改动文件、验证结果、风险、未完成项
```

不要在子 Agent 提示中省略关键上下文后再要求它自行猜测。

### 侦察模板

```text
只读调查 <范围>。不要修改文件。
目标：定位 <问题> 的相关调用链和根因候选。
必须检查：<目录、文件、日志或连接器>。
回报：关键证据（path:line 或命令输出）、结论、仍不确定的点。
```

### 实现模板

```text
在隔离工作区实现 <子任务>。
只允许修改：<文件或目录>。
遵守：<项目 Skill、AGENTS.md、接口和测试要求>。
完成后运行：<构建/测试>。
回报：实际改动路径、关键 diff、验证结果、剩余风险。
```

### 验证模板

```text
独立验证 <改动>，不要假设实现正确。
复现：<场景>。
执行：<命令或真实页面流程>。
重点：<回归、边界、并发、权限、视觉宽度等>。
回报：通过/失败、原始证据、失败步骤、最小修复建议。
```

## 执行流程

1. 读取项目规则，确认仓库、分支、工作区和未提交改动。
2. 写明成功标准和验证面；不明确时先做最小必要调查。
3. 快速列出独立工作流，决定单 Agent 还是并行。
4. 并行完成侦察，主 Agent 同时处理不依赖结果的本地关键路径。
5. 锁定写入范围和接口，再委派独立实现任务。
6. 实现期间继续做集成、测试准备或外部资料核对，不空闲等待。
7. 用当前环境提供的 Agent 等待/汇总工具在确实阻塞时等待，不要反复轮询。
8. 审查子 Agent 结果；拒绝无证据、超范围或验证失败的结果。
9. 运行最终质量门禁，并做一次独立 Review。
10. 关闭不再需要的子 Agent，清理临时资源，输出精简交付说明。

## 工具选择

| 需求 | 优先方式 |
|---|---|
| 固化项目规则 | `AGENTS.md`、仓库级 Skill |
| 复用流程 | 已有 Skill；没有再用临时提示 |
| 并行调查 | 子 Agent |
| 互斥模块实现 | 子 Agent + 独立写入范围 |
| 后台隔离开发 | worktree；用户可见切换先征得确认 |
| 主工作区构建/运行/调试 | IDEA MCP |
| worktree 构建/测试 | PowerShell `mvn` |
| 代码评审 | `/review` 或独立评审 Agent |
| 前端真实验证 | 浏览器、CDP、真实 Chrome、截图和 Console/Network |
| 周期检查 | automation；先手工验证提示，再保存 |
| 外部系统 | MCP、插件或连接器 |
| 长时隔离任务 | Codex Cloud，前提是用户和要求允许 |
| 文档/表格/PDF/演示 | 对应文档工件 Skill |
| 官方能力核对 | `openai-docs` Skill |

不要同时启动多个会写同一工作区、数据库记录或外部系统的子任务。

## 自动化提效

只有任务会重复发生且用户明确要求自动化时，才建议 automation：

- PR/CI 持续巡查。
- 新评审意见跟进。
- 部署或长任务完成提醒。
- 周期性日志、依赖或安全扫描。
- 日报、周报和固定格式报告。

不得自行创建或修改 automation；用户确认后，创建前：

1. 先用普通任务手工验证提示和访问权限。
2. 明确什么变化值得通知。
3. 状态未变化或不可操作时保持静默。
4. 需要用户决定时再提醒，不制造周期性噪声。
5. 更新已有自动化前先确认是否重复。

## 质量门禁

至少执行与改动风险匹配的验证：

- 读取最终 diff，而不只看子 Agent 摘要。
- 运行项目指定的构建、类型检查和测试。
- 前端不能只依赖类型检查；按项目要求做真实浏览器验证。
- 检查失败日志原文，不把“HTTP 200”或“命令返回”当成业务成功。
- 检查敏感信息、调试代码、本地配置和开发者模式内容。
- 检查分支、MR 目标和提交范围是否符合专用 Skill。
- 合并或交付前由主 Agent 做最终独立复核。

## 禁止事项

- 不因为提效跳过需求确认、构建、测试或 Review。
- 不自动 commit、push、merge、deploy 或修改生产数据。
- 不在多个 Agent 间共享未锁定的写入范围。
- 不为了并行而并行，不超过实际独立工作流数量。
- 不让子 Agent 在后台运行后无人检查结果。
- 不创建用户可见 thread 来替代内部子 Agent；除非用户明确要求新 thread。
- 不重复创建已有 automation。
- 不把子 Agent 总结当成证据。
- 不隐藏失败、跳过项和残余风险。

## 完成回报

最终回复保持精简，至少包含：

```text
完成：做了什么
验证：构建/测试/浏览器/评审结果
改动：关键文件或 MR
风险：未验证项、失败项、需要用户决定的事项
```

如果所有检查通过，明确写“通过”；如果有未验证项，要写清原因和影响，不得用“应该没问题”代替证据。
